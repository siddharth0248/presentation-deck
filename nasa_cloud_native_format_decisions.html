The Format Is Not the Decision

Target 1:00 | Evidence and narration are distinguished below.

Spoken explanation.

The upper path is a cautionary design pattern, not a reported incident. If the representation is chosen before the query, we can spend effort on conversion and only later find that the new layout does not help the user. The lower path starts with consumers and outputs, inspects the existing physical organization, and tests plausible options before publishing.

The original scientific product can remain authoritative while different access representations serve analysis and visualization. That separation gives us room to retain an adequate source path, create a bounded derivative, or choose a hybrid. Latency and throughput matter, but so do the update process, client support and the person responsible for the derivative. The format is the consequence of those decisions, not a substitute for them.

Caveats and presenter edits.

This slide is proposed engineering guidance from the brief. It does not assert a documented failure or an institutional standard.

Three Formats, Three Physical Models

Target 1:45 | Evidence and narration are distinguished below.

Spoken explanation.

The requested title says three physical models. More precisely, we are comparing two physical layouts with a virtual reference layer.

A COG places raster blocks and, where appropriate, lower-resolution overviews inside a GeoTIFF. The reader uses its index and selected resolution to retrieve the needed parts. Its spatial organization is chosen when the artifact is built.

Materialized Zarr stores array data using a deliberate multidimensional chunk grid and codecs. Layout can be chosen around the workload. Chunk and object are not synonyms: indexed sharding can pack inner chunks together. That creates an additional design choice, not a guarantee of faster reads.

Virtual access stores a description of array chunks and where compatible encoded bytes already reside. The client still needs those source bytes and a decoder. The reference does not contain the entire scientific dataset, and arranging references does not physically reorganize the source chunks.

The sketches show different locations for layout control. They do not compare measured speed. Each approach is only useful through a compatible reader and a maintained access path.

Caveats and presenter edits.

Terminology: Virtual Zarr is the approach; VirtualiZarr constructs virtual representations; Kerchunk is software and related reference representations; Icechunk is a storage implementation that can reference external chunks; Zarr v2/v3 specify different formats. Do not use these names interchangeably. Diagram proportions are schematic, not real file layouts or request counts.

Start With the Access Pattern

Target 1:30 | Evidence and narration are distinguished below.

Spoken explanation.

Consider three consumers of the same underlying collection. One wants a map window at a single time. Another wants one location or a small region through years of observations. A third computes across regions, dates and variables. These requests touch different parts of an array even though they use the same science data.

Record the requested dimensions and output, then ask whether the priority is quick first response or sustained throughput. Concurrency and locality change the workload, too. The same request repeated nearby is not the same as many scattered queries.

Next inspect the source organization and constraints. Can the source be retained? Are its chunks and codecs usable by the clients? How often will data be appended or revised? Finally, state the cost and ownership boundaries. These inputs narrow candidates, but none is an automatic winner. They also make the later benchmark reproducible.

Caveats and presenter edits.

The three query sketches are conceptual. Dask advises considering storage and memory when choosing chunking; no universal chunk size or request count is asserted. The relative advisor knobs are scenario controls, not measured quantities.

Decision Tree

Target 2:00 | Evidence and narration are distinguished below.

Spoken explanation.

This is a simplified view of the supplied scored advisor, not a new yes-or-no algorithm. A workload profile enters a shared sequence of checks. Every candidate starts at zero; all matching rules add their specified points, while cautions are retained separately. The result is sorted and then filtered for the selected data structure.

The recommendation set contains up to three compatible candidates within six points of the leader. That is different from the separate alternatives field, which returns the next three compatible candidates. These are heuristic preferences, not probabilities or predicted timings. The full rule tables are retained below.

The visible discussion focuses on raster and multidimensional access. The original advisor also includes NetCDF, GeoParquet, PMTiles and COPC. NetCDF remains an important existing-path baseline, even when a different representation is recommended for a consumer.

The dashed loop is an explicit addition for this talk: test the candidates on equivalent scientific work, record the decision, and revisit it if the workload changes. The hybrid and retain-existing-path option is also proposed guidance. A shortlist is the start of an experiment, not the end of the decision.

Caveats and presenter edits.

Do not interpret the advisor's exclusion of COG from its multidimensional compatibility set as a statement that TIFF cannot contain bands or time slices. The supplied empty-filter fallback returns the full ranking; proposed production behavior here is to stop and investigate. One metadata read or HTTP range reads are not universal backend requirements. Validate bounded initialization, selective retrieval and correctness for the deployed stack. No numeric case-study score or tie-breaking rule is invented.

## Purpose

The advisor selects cloud-friendly geospatial formats for one representative workload profile. It does not identify a universal winner. Every scenario starts with the same candidate formats, applies score adjustments from the selected inputs, removes incompatible candidates, and returns a ranked recommendation with trade-offs and validation steps.

## End-to-end flow

```mermaid
flowchart TD
    A[Start with workload profile] --> B[Read categorical inputs]
    B --> B1[Data structure]
    B --> B2[Primary access pattern]
    B --> B3[Archive context]
    B --> B4[Latency priority]
    B --> B5[Storage granularity]
    A --> C[Read relative 1-5 scenario knobs]
    C --> C1[Request locality]
    C --> C2[Update frequency]
    C --> C3[Cost sensitivity]
    C --> C4[Parallelism need]
    B1 --> D[Initialize all format scores at zero]
    B2 --> D
    B3 --> D
    B4 --> D
    B5 --> D
    C1 --> D
    C2 --> D
    C3 --> D
    C4 --> D
    D --> E[Apply data-structure rules]
    E --> F[Apply access-pattern rules]
    F --> G[Apply archive-context rules]
    G --> H[Apply request-locality rules]
    H --> I{Parallelism need >= 4?}
    I -- Yes --> I1[Add Zarr and GeoParquet points; record COG caution]
    I -- No --> I2[No parallelism score change]
    I1 --> J[Apply latency-priority rules]
    I2 --> J
    J --> K[Apply storage-granularity rules]
    K --> L{Cost sensitivity >= 4?}
    L -- Yes --> L1[Add COG and Virtual Zarr points; record Zarr caution]
    L -- No --> L2[No cost score change]
    L1 --> M{Update frequency >= 4?}
    L2 --> M
    M -- Yes --> M1[Add Zarr points; record COG caution]
    M -- No --> M2[No update-frequency score change]
    M1 --> N[Collect reasoning path, cautions, and anti-patterns]
    M2 --> N
    N --> O[Sort all formats by descending score]
    O --> P[Apply data-structure compatibility filter]
    P --> Q[Select top compatible format]
    Q --> R[Select close alternatives within 6 points]
    R --> S[Create recommendation set of up to 3 formats]
    S --> T[Generate guidance and validation checks]
    T --> U[Display recommendation and try-this experiment]
```

  Every scoring stage is shared by every data structure. For example, a multidimensional workload still reaches the cost-sensitivity check, and a raster workload still reaches the parallelism check. The checks only add points when their threshold is met; otherwise they pass through with no score change.

## 1. Inputs

### Categorical inputs

| Input | Values | Meaning |
|---|---|---|
| Data structure | `raster`, `multidimensional`, `vector`, `point-cloud` | The shape and semantics of the data. |
| Primary access pattern | `map-tiles`, `random-window`, `time-series`, `batch-analytics`, `ml-training` | How readers usually request subsets. |
| Archive context | `new-cloud-pipeline`, `existing-netcdf-archive` | Whether storage can be designed from scratch or must preserve a NetCDF archive. |
| Latency priority | `interactive`, `balanced`, `throughput` | Whether first response, a compromise, or sustained parallel reads matter most. |
| Storage granularity | `fine`, `balanced`, `coarse` | The desired balance between selective reads and object/request overhead. |

### Relative scenario knobs

Each knob is an integer from 1 to 5. These are relative scenario controls, not universal percentages or measurements.

| Knob | Low value | High value |
|---|---|---|
| Request locality | Broadly scattered requests | Repeated nearby windows or time ranges |
| Update frequency | Mostly static archive | Frequent append or rewrite cycles |
| Cost sensitivity | Performance-first | Request and storage cost is a primary constraint |
| Parallelism need | Low concurrency | Many simultaneous readers or workers |

## 2. Candidate formats

At the beginning of every evaluation, each candidate has a score of `0`, an empty list of reasons, and an empty list of cautions.

```text
COG | Zarr | Virtual Zarr | NetCDF | GeoParquet | PMTiles | COPC
```

The score is additive. Every matching rule increases a format score; caution rules only record a warning and do not subtract points.

## 3. Scoring rules

### Data structure

| Selection | Score changes |
|---|---|
| Raster | `COG +22`; `Zarr +10` |
| Multidimensional | `Zarr +24`; `Virtual Zarr +14`; `NetCDF +10` |
| Vector | `GeoParquet +26`; `PMTiles +12` |
| Point cloud | `COPC +30` |

The path also records why the selected data shape favors tiled, chunk-addressable, columnar, or hierarchical access.

### Primary access pattern

| Selection | Score changes |
|---|---|
| Map tiles | `COG +18`; `PMTiles +18` |
| Random window | `COG +16`; `Zarr +14` |
| Time series | `Zarr +20`; `Virtual Zarr +16` |
| Batch analytics | `Zarr +17`; `GeoParquet +12` |
| ML training | `Zarr +18`; `COG +10` |

### Archive context

| Selection | Score changes | Cautions |
|---|---|---|
| Existing NetCDF archive | `Virtual Zarr +25`; `NetCDF +8` | `Zarr`: full conversion can duplicate storage and add migration overhead. `COG`: conversion-only strategy may overproduce artifacts for nD products. |
| New cloud pipeline | `Zarr +8`; `COG +8` | None. Native cloud-ready publishing can be designed from the start. |

### Request locality

| Condition | Score changes |
|---|---|
| Locality `>= 4` | `COG +12`; `COPC +8` |
| Locality `<= 2` | `Zarr +8`; `GeoParquet +8` |
| Locality `3` | No locality-specific score change |

### Parallelism need

When parallelism is `>= 4`, add `Zarr +12` and `GeoParquet +8`. Also record a COG caution: single-object hotspots may limit parallelism at extreme scale.

### Latency priority

| Selection | Score changes |
|---|---|
| Interactive | `COG +8`; `PMTiles +10`; `COPC +6` |
| Throughput | `Zarr +8`; `GeoParquet +7` |
| Balanced | No additional score change; consider request overhead and scan throughput together |

### Storage granularity

| Selection | Score changes | Cautions |
|---|---|---|
| Fine | `COG +4` | Very fine Zarr chunks can increase metadata size and HTTP request counts. |
| Coarse | `COG +4`; `GeoParquet +4` | Coarse Zarr chunks may transfer substantially more data for small subset queries. |
| Balanced | No additional score change |

### Cost sensitivity

When cost sensitivity is `>= 4`, add `COG +10` and `Virtual Zarr +14`. Record a Zarr caution because fine chunks may increase object-storage request costs.

### Update frequency

When update frequency is `>= 4`, add `Zarr +8`. Record a COG caution because frequent reprocessing of large TIFF artifacts may increase pipeline cost.

## 4. Anti-pattern checks

These checks create warnings; they do not change the score.

| Condition | Warning |
|---|---|
| Existing NetCDF archive and cost sensitivity `>= 4` | Do not fully back-convert historical data to Zarr before validating access gains. |
| Multidimensional + time series + request locality `>= 4` | Do not use spatial-only chunking for time-series-dominant queries. |
| Raster + map tiles + parallelism need `5` | Do not assume one format optimizes map serving and deep analytics equally. |

## 5. Compatibility gate

After calculating and sorting scores, the advisor filters out candidates that do not fit the selected data structure. This prevents an incompatible format from appearing as a false winner.

| Data structure | Compatible formats |
|---|---|
| Raster | `COG`, `Zarr`, `Virtual Zarr`, `NetCDF` |
| Multidimensional | `Zarr`, `Virtual Zarr`, `NetCDF` |
| Vector | `GeoParquet`, `PMTiles` |
| Point cloud | `COPC` |

If the compatibility filter unexpectedly produces no candidates, the implementation falls back to the full ranking. Under normal inputs, the compatible ranking is used.

## 6. Ranking and recommendation set

```mermaid
flowchart LR
    S[Add score deltas] --> R[Sort descending by score]
    R --> F[Keep formats compatible with data structure]
    F --> W[Choose first format as winner]
    W --> N{Is candidate score within 6 points of winner?}
    N -- Yes --> A[Include as alternative]
    N -- No --> X[Exclude from recommendation set]
    A --> L[Limit recommendation set to top 3]
    W --> L
```

The returned result contains:

- `top`: the highest-ranked compatible format, score, reasons, and cautions.
- `alternatives`: the next three compatible ranked formats.
- `recommendationSet`: up to three formats whose scores are no more than 6 points below the winner. If none qualify, return the winner alone.
- `path`: an ordered explanation of each branch that was applied.

## 7. Format-specific follow-up output

After ranking, the top format selects layout guidance:

| Winner | Main guidance |
|---|---|
| COG | Tune internal tiles, build overviews, and avoid external ZIP/gzip wrapping. |
| Zarr | Align chunk shape and dimension order with the most common slices; balance over-read against request count. |
| Virtual Zarr | Inspect inherited source chunking; virtualize first, then rewrite only high-value workloads if needed. |
| NetCDF | Keep layout aligned with scientific access patterns and verify range-request support in the deployed reader. |
| GeoParquet | Partition and sort for spatial predicates, select required columns, and tune row-group size. |
| PMTiles | Pack tiles into one indexed archive and validate the hierarchy against actual zoom-level requests. |
| COPC | Preserve the spatial hierarchy and test local queries at multiple scales. |

## 8. Validation checks

Every result asks:

1. Can all required metadata be loaded with one predictable read?
2. Can a representative subset use HTTP range requests instead of a full download?
3. Does the selected latency profile avoid excessive request count and transferred bytes?
4. For an existing NetCDF archive, does virtual access beat a rewritten sample before full migration?
5. For a new cloud pipeline, has a representative sample been benchmarked before publishing the full collection?

## 9. Interactive experiment prompt

The advisor returns a `tryThis` prompt based on the winner, encouraging one controlled input change:

| Winner | Suggested experiment |
|---|---|
| COG | Switch access pattern to batch analytics and compare the leader against its closest competitor. |
| Zarr | Lower request locality by two steps and compare whether the leader remains ahead. |
| Virtual Zarr | Switch archive context to a new cloud pipeline and compare the new leader. |
| NetCDF | Raise parallelism need to `5` and see whether Zarr overtakes it. |
| GeoParquet | Switch access pattern to map tiles and see whether PMTiles closes the gap. |
| PMTiles | Switch access pattern to batch analytics and see whether GeoParquet overtakes it. |
| COPC | Lower request locality to `1` and observe whether point-cloud confidence changes. |

Case Study 1: When COG Makes Sense

Target 1:45 | Evidence and narration are distinguished below.

Spoken explanation.

For the first case, the workload is browsing the spatial pattern of one monthly MiCASA carbon-flux layer. The worked selection is heterotrophic respiration, Rh, for December 2010. The GHG Center notebook's saved monthly collection declares a cloud-optimized raster layer and links a month-and-variable asset to a raster map endpoint. This supports the COG publishing pattern, although this deck did not validate a TIFF itself.

The published asset grid in that saved metadata is 0.1 degree. The published Rh asset describes carbon flux from soil to atmosphere and uses grams of carbon per square metre per day, as a monthly mean. The notebook's collection narrative instead mentions kilograms; that conflict must be resolved against the actual asset before numerical analysis.

The engineering reason for this candidate is spatial access at a selected month and map resolution. The diagram is not a scientific map. A multi-year point series would cross many monthly assets and should be tested separately. This is where a temporal derivative might earn its cost, not a reason to discard an otherwise useful map representation.

Caveats and presenter edits.

Presenter window is 2001-2025. The saved collection extent is 2001-01 through 2024-12; nearby prose says through 2023. The live catalog endpoint could not be retrieved. Preserve all three provenance levels and do not claim complete 2025 inventory. The exact native distribution and transformation version are unverified. No numerical map, sign conversion, overview statistic or scientific mean was computed.
