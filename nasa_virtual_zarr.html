The Cloud-Native Raster Problem.

The decision.Is a complete rewrite necessary for this workload?
GDAL COG · Zarr v3 core · Architectural framing02 / 15

Target duration. 1:30. Planned content totals 19:00 with a separate 1:00 buffer.

Spoken explanation.

An archive already embodies scientific and operational decisions. Before adding a new representation, we should ask what the consumer needs: a time series, a spatial slice, a regional reduction, or tiles for a map. The transformation path here is one possible path, not the definition of cloud-native access.

A physical derivative can be valuable because its layout can be chosen for a target workload. But it introduces work beyond writing files. Someone must choose how dimensions map into objects, retain or intentionally change the encoding, validate equivalent values and coordinates, publish the derivative and keep it in sync.

Recompression, rechunking and reprojection are choices, not mandatory steps in every transformation. We should also distinguish retained archival storage from added storage. The comparison in this talk assumes that the original scientific archive remains available under either design.

The alternative is not to remove every one of these responsibilities. It is to ask which responsibilities can move into a lighter logical layer while the source chunks remain in place.

Transition. Compare the three representations by their physical and logical organization rather than by a universal ranking.

Demonstration status and caveats. Architecture explanation. No conversion was executed and no conversion cost was measured.

GDAL COG · Zarr v3 core · VirtualiZarr serialization · Kerchunk03 / 15

Target duration. 1:15. Planned content totals 19:00 with a separate 1:00 buffer.

Spoken explanation.

These diagrams are deliberately simplified. COG represents raster data with a physical organization designed for selective access, including overview choices. Physical Zarr represents multidimensional arrays in chunks whose organization can be chosen when data are written. A virtual representation presents a compatible logical chunk grid while referring to bytes that already exist.

The categories are not a ranking. Icechunk itself can contain native chunks and virtual chunks, and a production workflow may expose both an analysis representation and a visualization-oriented derivative. Likewise, the Zarr specification is a data model and storage specification, not a promise that every implementation supports every extension.

Terminology matters. Virtual Zarr is the approach. VirtualiZarr is a library used to construct references. Kerchunk is a software project and also the origin of reference representations. Icechunk is a storage engine with its own repository and session model. None of those names is interchangeable with a Zarr format version.

VirtualiZarr 2.0.1 · Icechunk 1.1.1 · S3 GetObject04 / 15

Target duration. 1:15. Planned content totals 19:00 with a separate 1:00 buffer.

Spoken explanation.

Follow one read rather than one file conversion. The client first selects a logical chunk. The compatible store resolves that chunk to reference metadata. That metadata identifies the source object and relevant byte range. The original bytes are fetched and decoded using compatible codecs before array values are returned.

The blue square is only a schematic selected chunk. The reference layer is not drawn as if it holds the whole scientific payload. Depending on implementation, small coordinate arrays or other native chunks can also be stored alongside the references.

This explains both the attraction and the limitation. A full second payload copy may be avoided, but source-data reads, manifest reads, caching, authentication and decoding still exist. Virtualization does not promise zero data movement, zero storage or zero I/O. Nor does it replace metadata validation or scientific quality control.

Spoken explanation.

The public example gives us a concrete NLDAS read-back path, and its lockfile gives us an older but identifiable software environment. This slide combines that evidence with the released library APIs to show a construction recipe. It is not a claim that we reran the original build.

Inspection comes first. Confirm the selected daily forcing product, file ordering, dimension coordinates, encodings and chunk layout. A matching array shape alone is not enough to establish compatible scientific meaning.

Reference generation parses compatible source files. Combination joins the logical records in a known order. That is different from physically rechunking the payload. Persisting the representation writes a repository and creates a committed snapshot. Validation must compare a sample with the original files before the published representation is trusted.

The final step is a genuine handoff. A construction-time virtual dataset is an assembly object. The analytical client opens the serialized store through a compatible reader. Do not call a mean or plot on the construction object and imply that it has read the scientific data.

Discovery is a different concern again. A catalog or access URL helps a user locate the finished resource; it does not generate the chunk references.

Spoken explanation.

The worked example is the beta daily meteorological forcing collection, not an NLDAS-2 substitution and not a demonstration of planned model outputs. The provider identifies beta forcing coverage from 2001 through 2023. The public documentation describes a nominal one-kilometer product on a latitude-longitude grid.

The engineering detail we will carry into analysis and evaluation is the daily source chunk. For a variable such as Tair, its source shape is one time step by five hundred latitude cells by nine hundred longitude cells. The diagram illustrates that layout, not geography and not measured I/O.

This suggests a workload question. A small selection across many dates may intersect a different pattern of chunks than a spatial slice at one date. Whether that matters in practice depends on the client, compression, cache and request concurrency. We will not convert the diagram into a claimed speedup.

The feasibility working group describes the NLDAS virtual-store example as early development. That is useful context, not a NASA-wide production endorsement. We also avoid using its reported total archive size as a measurement of this exact subset.

The registry connects source URLs to an authorized object-store reader. The HDF parser is appropriate for compatible NetCDF4/HDF5 input, not for every possible NetCDF format. Time and dimension coordinates are loadable; the scientific data variables remain virtual references.

# Adapted from inspected APIs; NOT executed in this environment.
# Use Python 3.12 and the NLDAS-icechunk uv.lock environment.
# Key pins: virtualizarr==2.0.1, icechunk==1.1.1,
# xarray==2025.6.0, zarr==3.1.1, obstore==0.7.3.
import tempfile
from pathlib import Path
import icechunk
import xarray as xr
from obstore.store import S3Store
from virtualizarr import open_virtual_mfdataset
from virtualizarr.parsers import HDFParser
from virtualizarr.registry import ObjectStoreRegistry

bucket = "nasa-waterinsight"
root = f"s3://{bucket}"
source_prefix = f"{root}/NLDAS3/forcing/daily/"
# Three candidate files from the provider's documented naming pattern.
# Existence and their time bounds must be verified before running.
urls = [
    f"{source_prefix}202001/NLDAS_FOR0010_D.A{day}.030.beta.nc"
    for day in ["20200101", "20200102", "20200103"]
]
registry = ObjectStoreRegistry({root: S3Store(
    bucket=bucket, region="us-west-2", skip_signature=True
)})
config = icechunk.RepositoryConfig.default()
config.set_virtual_chunk_container(icechunk.VirtualChunkContainer(
    source_prefix, icechunk.s3_store(region="us-west-2")
))
credentials = icechunk.containers_credentials({
    source_prefix: icechunk.s3_anonymous_credentials()
})
# A new LOCAL destination. Never overwrite the published source/store.
destination = Path(tempfile.mkdtemp(prefix="nldas-vz-")) / "references"
storage = icechunk.local_filesystem_storage(path=str(destination))
build_repo = icechunk.Repository.create(storage, config, credentials)

Validation gate.

Open the committed local repository via a new read-only session. Verify a non-empty, unique, increasing time index and consistent lat/lon coordinates. Read equivalent original-file samples with an appropriate NetCDF backend, with the same CF mask/scale/time decoding, and use xarray.testing.assert_allclose on values after checking coordinates, units and masks separately. Where Virtual Zarr Breaks Down.

◇ General engineering risks. Not observed failures here.
01

Long point histories can intersect many broad spatial chunks.

02

Many small objects or fragmented reads can dominate access.

03

The hard limit.A logical representation cannot repair a physical layout mismatch.
VirtualiZarr / Icechunk implementation · Co-Working Group limitations, not NASA policy12 / 15

Target duration. 1:30. Planned content totals 19:00 with a separate 1:00 buffer.

Spoken explanation.

These are general engineering risks, not failures we observed during a build. The source chunk layout sets the physical granularity of reads. A virtual layer can reorganize the logical view but does not change where the original compressed bytes live.

Request amplification is a separate issue from logical dataset size. Many small files, fragmented selections and ineffective caching can increase overhead. Measure the requests and the transferred bytes rather than assuming that a small returned array implies small network traffic.

Compatibility is scientific as well as syntactic. A decoder must support the codecs in use. Coordinate systems, fill values and scale/offset encoding must remain consistent. Combining files that look superficially similar can still produce an incorrect result, so the validation gate must be explicit.

Finally, references depend on source identity and authorization. Repository versioning alone does not freeze externally managed source objects. A changed object, a removed file or an expired access path can invalidate a previously usable reference.

This is not a blanket statement that virtual workflows are read-only. Supported stores can commit new references or native chunks. That is different from mutating the referenced original source bytes in place.

Transition. Convert those risks into production decisions, including when to use a hybrid.

Demonstration status and caveats. General documented limitations and working-group risk observations. No failures were observed or repaired in this task. Writable repository evolution is distinguished from source-payload mutation.

Workload-first recommendations · NASA Co-Working Group report · URL proposal caveats in notes13 / 15

Target duration. 1:30. Planned content totals 19:00 with a separate 1:00 buffer.

Spoken explanation.

The first recommendation is workload-first design. Inspect the existing physical layout before deciding to virtualize or rewrite. A format label does not tell us whether the source chunks match a point series, a regional analysis or a map request.

Second, make equivalence testable. Retain a small suite that compares source and virtual views using the same decoding rules. Include coordinates, masks and time interpretation rather than only checking a few numeric values.

Third, version both sides of the relationship. Record the reference snapshot, the identities of the source objects and the tested client environment. Assign an owner for rebuilds, updates and deprecation. Source reprocessing and upstream software changes are different triggers and should not be handled accidentally.

Fourth, operate the read path. Repository access does not automatically authorize source access. Monitor failed reference reads, request volume, transferred bytes, memory and latency for the workloads users actually run.

The diagram is a recommendation, not a claimed deployment: keep broad archive access virtual where it works, and materialize hot subsets or visualization products selectively. Discovery belongs alongside this architecture. A canonical identifier can locate the resource, but it is not the process that created its references.
